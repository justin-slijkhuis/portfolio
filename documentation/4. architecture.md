# Architecture

![Architecture](diagrams/Architecture/Architecture.svg)

As seen in the picture, I came up with three different architectures which I tweaked a bit to solve the issues I found. Below each architecture is described and eventually a conclusion is given.

Some decision that were which aren't really shown in the architecture. One is that the website(s) are going to be build using Qwik. Qwik is a newer JavaScript framework made by old React developers that is build for speed. Since I have set some high performance standards, this framework is the best choice compared to all the other frameworks. Downside is that the community will not be able to help that much since it is a newer framework.

The other decision is that I will use PostgreSQL. The reason for this is mainly that I really started liking it after using it for a little while. I wanted to use a SQL database since I need the data to be both consistent and related to each other. A NoSQL database like Neo4J would be a good choice for the relations, but a bad choice for keeping data consistent. Neo4J is also way more expensive and harder to host than PostgreSQL. PostgreSQL comes with a ton of features and is very optimized meaning it can be quite quick.

## Shared decisions

Some decisions are shared between the architectures. For example, you don't see any caching in the architecture. This is because caching isn't needed here. The website isn't expected to have a lot of traffic and the data is expected to change a lot. Besides, most of the architecture websites literally have the database right next to them meaning the data is already quite fast to retrieve.

## Architecture 1.0

The first architecture is just a website with a database. The portfolio and CMS would be the same Qwik website which is very helpful for building the post part of the CMS. Yet this does make it harder to apply good security since the security needs to be applied to certain URLs instead of the entire website. Issues at the CMS part would also cause issues at the Portfolio part since it could break the entire website. This is not a good thing since the portfolio part should always be available.

## Architecture 2.0

The second architecture introduces an API. The reason for this is that it moves the security from the website to the API. This makes it easier to go against SQL injections and to make sure I am the only able to use the CMS. So this solves the security issues. This does introduce other issues like slowing down the website a bit, requiring more time to finish the product, costs go up and there is now a dependency on the API. If the API crashes, then the portfolio does not work. So now either the API or the CMS could crash the Portfolio which is not what we want.

To solve some of the issues of 2.0, I made 2.1 which uses GraphQL instead of REST. This is because GraphQL is optimized for retrieving data which is mainly what the Portfolio part does. This would make the website faster and the API less of a bottleneck. Yet this would increase cost even more since GraphQL requires more resources.

## Architecture 3.0

The third architecture splits the website into two different websites. One for the portfolio and one for the CMS. This way the portfolio can't break if the CMS ends up crashing. It also allows me to apply the security to the entire CMS website which is located on a subdomain. It is also impossible for the CMS to slow down the portfolio which it was able to before if I were to ever make a coding mistake. Yet the 3.0 version makes implementing the post part of the CMS harder since it does not have the same components unless I copy paste it.

To fix the issue of 3.0, I made 3.1 which introduces a component library. Both websites import the component library. Changes to the component library will be applied to both websites. However, both do need to install the update which means they could go out of sync. It also adds more complexity to building the websites.

So version 3.2 was made to fix those issues. It introduces a component library server. This is basically a Qwik website which only contains components. Using module federation, both websites can retrieve the components from the component library server. This way they are always in sync. Yet it does increase complexity and cost even more.

So lastly there is version 3.3 which is quite the same as 3.2. The difference is that the portfolio website acts as the component library server. So the CMS website retrieves the components from the portfolio website using module federation. This way there is no need to host another website which reduces costs and complexity. Yet using module federation this way is experimental in my book, so this would require another prototype to see if it works.

## Architecture 4.0

Then lastly there is architecture 4.0 which is a combination of 3.3 and 2.1. It is basically everything described for version 3.3 except for the fact it doesn't directly communicate with the database, but with GraphQL instead. This makes this project way more secure than before. It also makes it easier to scale which might come in handy in the future for the post section. The downside is that it increases cost and complexity even more. It also introduces a dependency on the API which could break the portfolio.

The architecture also includes a Redis database which is used for rate limiting to ensure the API doesn't get spammed. This is a very important feature since someone could try and break the API by sending a lot of requests. This would make the API slow down and eventually crash. The reason for using Redis is that is is both simple to implement rate limiting and it also allows me to scale the API horizontally if ever needed.

## Conclusion

In the end the decision is to use version 4.0. This means that I will be building the Portfolio and the CMS as two separate websites. Both websites will use a GraphQL API which uses the database. The main reason for this choice is security. So the next step is to build a prototype to test module federation in Qwik. This could be a challenge since Qwik does not use Webpack by default. The prototype will also contain a GraphQL API since I have never build one before. This is to see exactly how it works and to validate my choices in the architecture.
