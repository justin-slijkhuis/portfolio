# Prototype posts

As mentioned in the database design, I have created a prototype to come up with a way to build, store and edit posts. The main issue here was to store the posts in a way that is efficient. In the database design I had a few ideas which I tested.

## Storing posts

As described, I wanted to test dangerously specifying inner HTML. This is a feature of Qwik which allows me to use text as a way to build a page. This is done by using the `dangerouslySetInnerHTML` attribute. Now I tried using this and specifying actual HTML works. The issue is that it only works for HTML and not for Qwik components. First I thought maybe that could work if I parse the components to actual HTML which is what would be stored in the database. Yet this would break the editing functionality since I would have to parse the HTML back to components to be able to edit properties of the components. It would also break custom functionality for the different components. Changes to components would also only apply to the new pages.

So I decided to try one of the other options which is storing the components in an array of JSON values. This is what I have done in the prototype. Below is an example of how a post is stored in the database. It consists of a key specifying the component to use, the properties that have been set and the children that a component has. This is a recursive structure which allows for infinite nesting of components.

```json
[
    {
        "component": "Group",
        "props": {
            "left": {
                "value": 500,
                "unit": "px"
            }
        },
        "children": [
            {
                "component": "Heading",
                "props": {
                    "level": 1,
                    "text": "This is a level 1 heading"
                },
                "children": []
            }
        ]
    }
]
```

## Building posts

Loading posts using JSON works beautifully. Using TypeScript it also allows me to specify the data types/options that certain properties have. Like how the unit property requires a value from the Units enum. This is a great way to build the menu to edit the properties of the components. I do want to specify a default value for the non-nullable properties to make sure the page doesn't break when a property is missing.

This prototype contains a small editor. The editor allows me to click on one of the cards to add the component to the page which shows the building part. It also displays two inputs at the top for the group properties. Being able to change properties was a bit of a challenge since reflection isn't something that TypeScript has. The idea was to read the properties and their data types from the interfaces which contain the possible properties. That way it would automatically generate the inputs for the properties. Sadly I did not get that to work. So instead each component needs their own settings component that is opened when the component is pressed which contains the inputs for the properties.

Since components are probably going to change in the future, there also needs to be a way to update the components. This is something that isn't in the prototype. The current idea is to add a CMS version number to all the posts. Every time a new CMS version is released, then it will also contain an update script just like how application have database migrations. So when the post is loaded in either the portfolio or the editor, then it will check if the post is up to date. If it isn't, then it will run the update script which will update the post to the latest version.

## Conclusion

Posts will be stored in JSON format inside the database. The portfolio will retrieve the JSON using the post_id and use it to generate the post for the user. The post consists of a ton of components. Each component will get a mapper which maps the JSON to the actual UI component. So if the JSON key named component has a value of "Group", then it knows to use the mapper for the Group component. The mapper will use the properties and children specified in the same JSON object to create the UI component which will be displayed in the page.

The CMS part will create the post JSON based on the input of the owner. This input starts by clicking on components to add them to the visual editor. Here we must allow the owner to change the order of components so that a newly added component does not stay at the bottom. The components that the owner can use are going to be specified like the allowedComponents array below. Preferably this array will also contain the component itself so that the owner can view what the component looks like with their default settings before adding them to the visual editor.

```typescript
interface ComponentElement {
    name: string;
    description: string;
}

export const allowedComponents: ComponentElement[] = [
    {
        name: 'Heading',
        description: 'A heading component',
    },
    {
        name: 'Group',
        description: 'A group component',
    }
];
```

There will be a properties interface for every component which specifies the properties that the component has. This is used to make sure that the given properties are using the correct names and data types. It will also use enums to limit the options to a dropdown menu. Next there is a settings component for every UI component which contains the inputs for the properties. For instance, the owner can change the heading level of the Heading component using a dropdown menu. The settings component uses the properties interface so that the inputs must follow the names and data types of that UI component. The settings component is opened when the UI component is clicked on in the visual editor.

Lastly there will need to be two more things to ensure the posts editor works well. The first is to ensure that every non-nullable field has a default value. This is to prevent the page from breaking when a property is missing and also to hopefully display the component before adding it to the page. The second is to add a version number to the posts. This is used to check if the post is up to date with the latest changes. If it isn't, then the update script will be run to update the post to the latest version. This is done when the post is loaded in the editor. Updating to a newer version means changing properties, adding properties, changing component, etc. There is one rule and that is that it must not delete any data unless the owner specifically accepts it. This is to ensure that the post doesn't look completely different or even break when changes are made. Preferably we have another table that stores the history of the post so that the owner can revert to an older version if they don't like the changes.
